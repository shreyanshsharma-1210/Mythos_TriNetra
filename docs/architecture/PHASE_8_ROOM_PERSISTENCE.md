# Phase 8: Room Persistence Layer

This document details the architecture, database schema, threading model, and privacy constraints implemented in Phase 8 of TrustMesh 3.0, which transitions the security event storage from an in-memory repository to a local-first Room database.

## 1. Architectural Overview

The persistence layer integrates into the existing TrustMesh architecture without modifying the overall reactive behavior or introducing UI blocking. The real-time path remains untouched:
`Sensor -> SecurityEvent -> InteractionManager -> RiskEngine -> Overlay`

The new `RoomEventRepository` implements the existing `EventRepository` interface. It provides persistence backed by a normalized SQLite database via Android Room, serving as a single source of truth for historical interactions while allowing `InteractionManager` to manage an in-memory cache for instantaneous overlay updates.

### Normalization Strategy
The database schema is highly normalized to ensure data integrity and avoid brittle JSON serialization for complex relational data. The core `interactions` table stores base interaction state, while auxiliary tables handle lists of timelines, evidence, risk factors, and related security events.

## 2. Database Schema

The `TrustMeshDatabase` defines the following entities:

1. **`InteractionEntity`**: The root entity representing a unique interaction (phone call or notification group). Includes core metadata, risk level, resolved caller identity, and a timestamp optimized for sorting (`timestampMs`).
2. **`RiskAssessmentEntity`**: A one-to-one mapping to `InteractionEntity`, capturing the composite risk score, final risk level, and explanation generated by the RiskEngine.
3. **`RiskFactorEntity`**: A one-to-many relationship with `InteractionEntity`. Stores individual risk factors and their weights/sources that contributed to the assessment.
4. **`TimelineEntryEntity`**: A one-to-many relationship tracking the chronological sequence of events associated with an interaction. Preserves insertion order via `orderIndex`.
5. **`EvidenceEntryEntity`**: A one-to-many relationship storing arbitrary evidence strings related to the interaction, ordered via `orderIndex`.
6. **`SecurityEventEntity`**: Stores raw `SecurityEvent` instances for historical risk analysis, linking them to an interaction ID.

Relational data is queried efficiently using Room's `@Relation` capabilities via the `InteractionWithDetails` POJO, which automatically reconstructs the full `Interaction` model from the normalized tables.

### Data Converters
`TrustMeshConverters` securely translates Enums (`RiskLevel`, `EventType`, `IdentityType`, `IdentitySource`, `Confidence`, `RiskFactorType`) to and from their `String` names, ensuring structural integrity even if enum ordinal positions change in the future.

## 3. Threading & Reactivity Model

### Asynchronous Writes
To ensure zero UI latency and maintain real-time overlay rendering, all database writes (inserts, updates) are strictly asynchronous. The `InteractionManager` operates on a `CoroutineScope(Dispatchers.IO)` and fires-and-forgets writes to the repository:
```kotlin
scope.launch { repository?.insertInteraction(updatedInteraction) }
```
This guarantees that the overlay never waits for disk I/O before displaying protection UI.

### Synchronous In-Memory State
`InteractionManager` maintains its reactive `MutableStateFlow<List<Interaction>>` to drive the Jetpack Compose UI immediately. Upon application startup, `InteractionManager.init()` performs a one-time suspend call to load all existing history from the database into the `StateFlow`, seamlessly bridging persistent storage with fast reactive memory.

## 4. Privacy & Zero-Cloud Constraints

Phase 8 adheres strictly to the TrustMesh zero-cloud mandate:
1. **Local-First Storage**: Data is persisted entirely within the app's secure sandbox (`trustmesh.db`). No cloud synchronization, analytics, or external telemetry mechanisms are integrated.
2. **Minimal Data Retention**: Only metadata derived from the phone and notification sensors is stored. No audio, transcription, or raw payload content is captured or saved to the database.
3. **Standalone Architecture**: The repository continues to operate completely independently of external network dependencies.

## 5. Verification Status

Physical device verification guarantees:
- **Persistence Survival**: Interactions, historical timelines, and risk assessments survive application restarts and device reboots.
- **Real-time Performance**: The overlay continues to render instantly without visible stuttering or blocking from disk I/O.
- **Integrity**: De-duplication logic correctly updates existing database rows (via `@Insert(onConflict = OnConflictStrategy.REPLACE)` and targeted updates) instead of inserting duplicates.
